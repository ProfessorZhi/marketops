# MarketOps 调研插件：设计

适用版本：0.7 起。0.6.6 已有的部分和 0.7 要补的部分在第 9 节对照列出。

本文回答一个问题：一次调研从简报到交付，每一步由谁做（agent、脚本、批量模型调用），怎么并行，怎么保证质量。

## 0. 原则

1. **质量第一**：交付的每一条都必须经得起打开原页核对。速度和成本在不伤质量的前提下优化。
2. **证据规则**：邮箱必须原样出现在页面上，带来源页面和原文引用。脚本和 agent 都不许猜、不许手写邮箱。
3. **不丢只标**：弱证据、待复核、X 都保留并标注原因，由人或 agent 决定，不在中途静默删除。
4. **一套流程**：建池、挖掘、整理同时进行，按机构流动，不拆成彼此等待的几个流程（Bruce POOL-02）。
5. **人只拍板一次**：需要用户决定的事攒成一张编号清单（`needs_you`），一次问完；不停下来问"继续吗"。
6. **宿主无关**：Claude Code、Codex、WorkBuddy 都能完整使用；并行不依赖任何一家独有的功能。
7. **用真实结果衡量**：发版看真实对照和抽检，不看模拟。模拟只检查流程有没有出错。

## 1. 三种执行者，以及怎么分工

| 执行者 | 擅长 | 不擅长 | 在本插件里 |
|---|---|---|---|
| 脚本（Python 管线） | 量大、规则明确、要稳定可复现的活 | 临场判断、换策略 | 读页、抽取、搜索扇出、限速、断点续跑、合并去重、导出 |
| 批量模型调用（脚本里调） | 量大但判断很窄、每条独立 | 需要多步推理、要自己去找信息 | Jev 定级、线索排序、从引文里挑人名职位、范围判断 |
| agent（Claude Code / Codex / WorkBuddy 会话） | 开放问题、多步研究、根据结果调整策略、归属推理 | 慢、贵，同一问题两次结论可能不同 | 找来源、精挖、总结规律、复核、抽检、拍板前整理 |

分工判据，按顺序问：
1. 规则能写清楚、每家都一样？交给**脚本**。
2. 每条只要回答一个封闭问题（选项明确），但量大？交给**批量模型调用**。
3. 需要自己去找、要推理、要根据前面的结果改做法？交给 **agent**。

由此得出的分工原则是：**脚本负责覆盖面，agent 负责深度和判断，agent 学到的办法交给脚本放大。**

## 2. 工具层：六家 provider 加宿主自带工具

各家的用法细节在 `skills/marketops-tools/references/*.md`。这里只说谁调用、用在哪。

| 工具 | 能力 | 脚本用 | agent 用 |
|---|---|---|---|
| Serper | Google 搜索，快、便宜 | 深挖搜索的主力 | 找来源、精挖时搜 |
| SerpApi | Google/Bing/地图，结构化 | 地图查场馆、补搜 | 地图核对地点 |
| DeepSeek | 联网搜索加读页 | 读页竞速之一、搜索后备 | 难以描述的查询 |
| TinyFish | 搜索、真实浏览器读页，Agent 可点击 | 读页竞速之一；按钮后的邮箱（`browse`，按步计费） | 要点开或登录墙后的页面 |
| Crawl4AI | 本地浏览器抓页，免费 | 读页主力 | 大批读同一站 |
| Jev（TypeSafe） | 结构化多选判断，带概率 | 定级、排序、人名职位、范围判断 | `judge` 批量判断一列 |
| 宿主 WebSearch / WebFetch | 宿主自带 | 不用 | agent 临时查资料（结论要入库，仍须用 `fetch` 读页） |

规则：
- 凡是要进入交付的页面，必须走插件的 `fetch(project, url, org_id=...)`。只有这样地址才带上来源和引文、进库和成本账。宿主的 WebFetch 只用来看，不用来入库。
- 每次调用都记账（`costs.jsonl`）；付费账户以首次读到余额的 10% 为红线，低于红线就跳过这家，其余照常；余额问题进 `needs_you`。

## 3. 工作流：五个阶段

```
简报 ─▶ 建池 ─▶ 挖掘 ─▶ 整理 ─▶ 交付与学习
        ▲  agent找来源  │ 脚本广扫        │ 规则+模型定级
        │  脚本入池     │ agent精挖       │ agent复核/抽检
        └──────────────┴─ agent学、脚本放大 ┘
```

各阶段不互相等待：池子里一有机构，挖掘就开始；挖掘一出地址，定级就开始；agent 随时补来源、领任务。

### 3.1 简报（agent 和用户，开始时一次）

- agent 读 `references/projects/` 里对应市场的文件，起草简报：目标、国家、语言、场景、等级定义、客户的地址规则、`routes_per_org`、排除项、当地岗位词。
- 缺的信息一次问齐（marketops-brief 列了必须定下来的问题）；定下的写进 `brief.json`，之后不再反复问。
- 用户中途纠正口径：agent 更新简报，`grade(regrade=True)`，并用 `learn` 写进项目文件。

### 3.2 建池（agent 为主，脚本入池）

| 步骤 | 谁 | 做什么 |
|---|---|---|
| 找来源 | agent（来源组） | 按 marketops-sources 的顺序找：一次返回整份名单的来源（名录、开放数据、联合会、CMS 接口）优先；问客户已有名单；搜索是最后手段 |
| 验证来源 | agent | 先看 20 行，确认这份来源的每一行到底是什么（Bruce：慈善代码 108 是宗教机构，不是体育） |
| 入池 | 脚本 | `fetch` 下载导出文件，用 `pool(...)` 入池；合并键是名称加地点，网站只作参考 |
| 衡量来源 | 脚本 | 每个来源跑满 30 家后算 A/B 产出：≥10% 加倍轮次，5–10% 改进一次，<5% 排到最后 |
| 补来源 | agent | 看各来源的产出和覆盖缺口（类型、地区），继续找下一个来源 |

池子不在开跑时定死。来源组一直工作，直到来源用尽，或简报规定的覆盖面已经达到。

### 3.3 挖掘（脚本广扫，agent 精挖，agent 学、脚本放大）

**3.3a 脚本广扫（每家都做）**
- 没有官网的，按名字加城市找一次官网；域名解析不了的，重找现行官网。
- 读高价值页面：人员、团队、董事会、联系、法律声明页优先，PDF 也读。共用门户上只读本机构那一页及其下层。
- **页数按收益动态决定**（0.7）：只要还在读出新地址就继续，翻页名录跟到底；连续两页没有新东西就停；设总上限和每站时间预算。
- 每页三个读取器竞速，最快的先用，慢的在后台补；搜索各引擎同时查。
- 没有确认 A/B 的，按模板深挖几轮：市场岗位词、站内搜索和 PDF、名录和联合会、地图、广搜。
- **深挖预算按类型分配**（0.7）：一类机构跑满 30 家后，深挖产出低于 5% 的只挖 1 轮，把剩下的机构交给 agent 精挖。

**3.3b agent 精挖（脚本挖不到的机构）**
- 范围：广扫后仍没有确认 A/B 的机构。顺序：先按客户价值，再按"同类里 agent 成功率高"排序。
- 做法：像研究员一样逐家挖，例如站内深处、会议纪要 PDF、市政公报、辖区和区属页面、联合会子页面、其他拼写、地图。
- 要求：每页都用 `fetch(org_id=...)` 读；每家结束写一行"找到了什么、在哪类页面、为什么判这个等级"；归属不清的标 review，不硬判。
- 并行：由任务队列派发（`tasks(kind="dig")`），多个 agent 会话同时领。

**3.3c agent 学、脚本放大（控制成本的关键）**
- agent 每挖完一类机构（例如"巴黎市属体育中心"）的 30 家，就总结一份这类机构的找法：联系人在哪类页面、URL 有什么规律、用什么搜索词能找到、谁是对的岗位。
- 找法写进简报（`focus` 加类型规则）和 `references/projects/`；脚本用新找法把同类剩下的机构全部重挖一遍。
- 这样 agent 只需深挖每类的一个样本，大部分机构由脚本按 agent 的方法完成。

**3.3d 难页**
- 邮箱藏在按钮后、要交互的页面：`browse`（TinyFish Agent，按步计费），只在有额度、且简报允许时使用。
- 被 Cloudflare 按 IP 拦截的：换读取器；仍不行就记下原因，不反复重试。

### 3.4 整理（规则、模型、agent）

| 步骤 | 谁 | 做什么 |
|---|---|---|
| 地址规则 | 脚本 | 客户排除的地址（如 info/admin/book）入库时直接定为 X，不调用模型 |
| 定级 | Jev | 每条候选按简报的等级定义判 A/B/C/D/X，带概率；同一机构、同一地址、同一引文只判一次 |
| 硬规则 | 脚本 | A 必须有人名；归属不清（地址挂在多家下且引文没点名、他站页面没点名、门户域名）、低置信度的，进待复核 |
| 佐证 | 脚本 | 对 A/B 再搜索交叉验证，提高证据分 |
| 复核 | agent（复核组） | 领取待复核的行：打开原页、读引文、对照简报下结论，用 `grade(set=...)` 写回并附理由；判不了的才进 `needs_you` |
| 合并去重 | 脚本 | 同一人两个地址只计一条路线；按机构汇总，选首选联系人（确认的 A/B 优先） |
| 抽检 | agent | 交付前从确认 A/B 里随机抽 100 条，逐条对照原页面核对，算准确率，写进工作簿 |
| 导出 | 脚本 | 工作簿（说明、对账、机构、联系人、来源、过程、成本、X）和 18 列路线 CSV |

### 3.5 交付与学习

- 交付前检查：对账对得上；国家、地区、场景没有空的；抽检准确率 ≥ 90%；`needs_you` 已问过用户。
- 交付物叫"研究有效邮箱"，不叫"可发"。本插件不发信，发信侧需要的字段见 `references/outreach.md`。
- 项目结束时 agent 跑 `learn`，把来源产出、有效页面类型、岗位词、纠正、找法写进 `references/projects/<市场>.md`，下个项目从这里起步。

## 4. 流水线与并发

### 4.1 机构的流转

```
queued ─▶ site ─▶ grading ─▶ digging ─▶ evidence ─▶ done(script)
                                 │
                                 └─▶ agent_dig ─▶ review ─▶ done
```

每家机构独立流转，任何时刻不同机构处在不同阶段。状态写在磁盘上（`crawl.csv`、`trace.jsonl`、`run.*.json`），进程重启后从磁盘续跑。

### 4.2 队列

| 队列 | 谁往里放 | 谁领 |
|---|---|---|
| 来源队列 | agent、用户 | 来源组 agent |
| 机构队列 | 入池 | 脚本分片 |
| 精挖队列（`dig`） | 脚本（广扫后没有确认 A/B）、agent | 精挖组 agent |
| 复核队列（`review`） | 硬规则 | 复核组 agent |
| 难页队列（`browse`） | 脚本 | 难页组 agent 或 TinyFish Agent |
| 决策清单（`needs_you`） | 以上所有人判不了的事 | 用户，一次答完 |

### 4.3 脚本层并发（0.6.6 已有）

- N 个分片进程（`run(shards=N)`，巴黎跑测用 4），每个同时处理 24 家机构；supervisor 负责重启死掉的分片。
- 每页三个读取器竞速；每家 provider 一个线程池，互不拖累；按各家官方限速自适应，遇到 429 自动调整。
- 定级在后台批量做，不阻塞挖掘。

### 4.4 agent 层并发（0.7）

- 角色：来源组、精挖组、复核组、难页组。角色说明写在 `references/roles/*.md`，与宿主无关。
- 协调：全部经由任务队列。领取时带 40 分钟租约，超时收回重派；同一任务不会被两个人同时领。
- 默认规模：来源 2、精挖 2–4、复核 2、难页 0–1，可在简报里改。
- **写入互斥**（0.7 必须做）：agent 领到某家机构时，脚本暂停处理这家，避免两边同时写同一家的联系人；脚本处理中的机构不派给 agent。
- 写文件安全：联系人按机构分文件；临时文件名带进程号和线程号；共享文件加锁。

### 4.5 主会话（协调者）做什么

1. 起草简报，一次问齐。
2. 启动管线（`run`），按宿主能力启动 agent（见第 7 节）。
3. 盯整体，不盯细节：每隔一段时间看 `project()` 的进度、各来源产出、`ab_routes_per_30_min`、需要处理的队列长度。
4. 把 `needs_you` 一次性交给用户；收到答复后写回。
5. 跑完后：抽检、导出、`learn`、汇报。

## 5. 质量体系

| 层 | 措施 |
|---|---|
| 证据 | 每条都有来源页和引文；不猜邮箱；agent 也只能用 `fetch` 入库 |
| 归属 | 合并键用名称加地点；共用门户只有本机构那一页算本站；共用地址、他站页面没点名的进待复核；点名检查要求机构名里最少见的那个词出现 |
| 定级 | 简报写清等级定义和当地岗位词；客户规则优先；A 必须有人名；按实际负责场地、设备、外包的人排，不按职位高低 |
| 复核 | 脚本把可疑的标出来，agent 先判，判不了的才给用户 |
| 抽检 | 每次交付抽 100 条确认 A/B 人工或 agent 核对，准确率 ≥ 90% |
| 金标准 | 每次发版跑 Bruce 法国 249 家已定级账户的真实对照：有 A+B 的机构占比 ≥ 37%（他的 1.3 倍），A 的数量不少于他，准确率 ≥ 90% |
| 回归 | 单元测试覆盖每一条规则；模拟检查流程（速度、路线、误报、陷阱） |

## 6. 怎么衡量

- 广度：有确认 A+B 的机构占比；每百机构 A+B 路线数（另报每机构最多 3 条的口径）。
- 精度：抽检准确率；金标准对照。
- 速度：每分钟机构数、`ab_routes_per_30_min`、各阶段秒数（`trace.jsonl` 和"过程（耗时）"页）。
- 成本：provider 花费（`costs.jsonl`）和 agent 的 token 分开报；每家机构的成本、每条 A+B 路线的成本。
- 投入：用户插话次数；`needs_you` 的条数。
- 贡献：每个来源、每个阶段、每个读取器、agent 精挖各自新增了什么（"贡献（消融）"页）。

## 7. 宿主适配：Claude Code、Codex、WorkBuddy

| 层 | 内容 | 适配方式 |
|---|---|---|
| 核心 | Python 脚本加 MCP server（stdio） | 三家都挂同一个 server；后台进程由 server 管，不依赖宿主 |
| 知识 | skills、`references/` | 一份源文件，按宿主格式生成清单和放置位置 |
| 角色 | `references/roles/*.md` | 与宿主无关的角色说明 |
| 协作 | `tasks()` 队列、`needs_you` | 谁连上 MCP 谁就能领活 |

启动 agent 按能力选，不按宿主写死：
1. 能起子代理（Claude Code）：自动起 `marketops-worker`，每个指定一个角色。
2. 不能起子代理、但能开多个会话（Codex 的 `codex exec`、WorkBuddy 多线程）：主会话输出每个角色可直接粘贴的启动语，用户多开几个会话。
3. 都不行：主会话自己轮流处理各队列，慢一些，流程不变。

各宿主接入状态：Claude Code 已完成；Codex 要补清单和 MCP 配置（0.5.x 旧插件有，0.6 重写时没带过来）；WorkBuddy 的配置格式要在真机上验证后再写。

## 8. 与 Bruce 经验的对应

| Bruce 的痛点或要求 | 本设计的对应 |
|---|---|
| 时间耗在"等"和"重做"上 | 各阶段不互相等待；状态写在磁盘上，断点续跑；死进程自动重启 |
| 流程不能停、不能停下来问"继续吗" | 一次简报、一张编号清单，其余自动推进 |
| 状态要说真话 | 进度按磁盘上的结果算 |
| 数要对得上 | 对账一行；每行都带国家、地区、场景 |
| 人工复核做不完（13 次） | agent 先复核，只有判不了的才给人 |
| 源头最重要 | 来源组一直在找；按来源产出分配轮次 |
| 规则要沉淀 | `learn` 写进项目文件；找法写进简报 |
| 不要更细的分片、更多线程 | 脚本层固定少量分片；agent 按角色分组，不按机构切碎 |

## 9. 现状（0.6.6）和 0.7 要补的

| 部分 | 0.6.6 | 0.7 |
|---|---|---|
| 脚本流水线、并发、重启 | 有 | — |
| 定级和硬规则（归属、点名、A 要人名） | 有 | — |
| 任务队列（领取、租约、收回） | 有，默认不用 | 默认启用；按角色派发；写入互斥 |
| 来源组 | 只有手动的 `custom` 任务 | 默认启动，持续补来源 |
| 精挖组 | 有 `dig` 任务，默认不用 | 广扫后自动派发 |
| agent 学、脚本放大 | 无 | 按类型总结找法，写进简报，脚本重挖 |
| 复核组 | 有 `review` 任务，默认不用 | 默认启动；`needs_you` 只放 agent 判不了的 |
| 动态页数、翻页跟进 | 固定 15 页 | 按收益决定 |
| 深挖预算按类型分配 | 无 | 有 |
| 抽检 100 条 | 无 | 交付前自动生成抽检表，由 agent 核对 |
| 金标准对照 | 定义了，0.6.x 没在真实网站上跑过 | 每次发版都跑 |
| Codex / WorkBuddy 接入 | 无 | Codex 补齐；WorkBuddy 真机验证 |
| agent token 计费 | 无 | 与 provider 费用分开报 |

实现顺序：
1. 写入互斥加角色派发：agent 层能安全地并行工作的前提。
2. 复核组和精挖组默认启动。

## 10. 先做的实验：agent 精挖能比脚本多找多少

做法：用 0.6.6 跑完一个项目后，从"没有确认 A/B、而且已经走完全部流程"的机构里分层抽样（各类型 10 家，固定随机种子）。由 agent 按 3.3b 的做法精挖，对比脚本阶段的结果。

衡量四项：
- 新增确认 A/B 的机构数和路线数；
- 人工核对后的准确率；
- 每家机构的耗时；
- agent 的 token 和 provider 的费用，两者分开报。

决策：
- 新增 ≥ 20%，且准确率 ≥ 90%：精挖组默认启动，并优先实现"agent 学、脚本放大"。
- 提升很小：问题主要在来源，agent 的力气优先放到来源组和复核组。
