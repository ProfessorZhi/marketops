# MarketOps 调研插件：设计（0.7）

本文回答：一次调研从简报到交付，整条业务链怎么由多个 agent 团队分段协同、同时推进；脚本、skill、业务知识、六家 provider 各自在里面做什么；怎么保证质量。

## 0. 原则

1. **质量第一**：交付的每一条都必须经得起打开原页核对。token 预算宽松，宁可多花 agent 的判断，也不要牺牲质量。
2. **证据规则**：邮箱必须原样出现在页面上，带来源页和引文。agent 和脚本都不许猜、不许手写邮箱；凡是要入库的页面，都走插件的 `fetch`。
3. **不丢只标**：弱证据、待复核、X 都保留并标注原因。
4. **分段流水、同时推进**：业务链分成几段，每段一个 agent 团队；段与段之间用池子交接；后一段不等前一段做完，池子里一有东西就开工。
5. **人只拍板一次**：需要用户决定的事攒成一张编号清单（`needs_you`），一次问完；中途不停下来问"继续吗"。
6. **宿主无关**：Claude Code、Codex、WorkBuddy 都能完整运行；并行只依赖任务队列，不依赖哪一家独有的功能。
7. **用真实结果衡量**：发版看真实对照和抽检；模拟只用来检查流程。

## 1. 组成部分

| 组成 | 比作 | 负责 |
|---|---|---|
| agent（Claude Code / Codex / WorkBuddy 会话） | 各段的研究员和组长 | 每一段的判断：找什么、去哪找、对不对、归谁、下一步怎么做；总结找法 |
| 脚本（Python） | agent 手里的批量工具 | 批量读页、抽取、搜索扇出、批量定级、合并去重、限速、记账、断点续跑、导出 |
| skill 和业务知识 | 培训手册和经验库 | 每段团队的作业说明；Bruce 六条业务线的经验（`references/projects/`）；各国来源、页面类型、岗位词、坑 |
| 六家 provider | 共用工具箱 | Serper/SerpApi 搜索、Crawl4AI/TinyFish/DeepSeek 读页、Jev 批量判断、TinyFish Agent 点按钮 |
| 插件（MCP server 加项目文件夹） | 办公室 | 工具接口、各级池子、任务队列、找法手册、成本账、编号清单 |

每个 worker 都是 **agent 加脚本工具**：agent 做主，对自己领到的每一项负责；脚本让它一次调用就能处理几十页、几十家。

## 2. 业务链：五段，五个池子

```
 段1 来源团队        段2 建池团队          段3 官网团队        段4 挖掘团队            段5 整理团队
 找数据源      ──▶   从来源抽出场地、  ──▶  为机构找到并      ──▶ 从机构挖出联系人   ──▶  复核、抽检、
                     归到运营机构           确认官网               并定级                  导出
     │                    │                    │                    │                      │
     ▼                    ▼                    ▼                    ▼                      ▼
 [来源池]            [场地池][机构池]      [已定位机构]         [联系人池]             [交付]
 sources.csv         venues.csv/orgs.csv   orgs.csv(网站)       contacts/              工作簿
```

每段都是"agent 团队加脚本工具"，从上一段的池子取活，往下一段的池子交货。五段同时在跑：来源团队还在找第 10 个来源时，挖掘团队已经在挖第 1 个来源出来的机构了。

### 段1 来源团队：找数据源

- **输入**：简报、对应市场的 `references/projects/*.md`、marketops-sources。
- **agent 做**：
  - 按经验顺序找来源：一次能给出整份名单的官方名录、开放数据、联合会、CMS 接口优先；然后问客户手里已有的名单；搜索放在最后。
  - 拿到来源先看 20 行，确认每一行到底是什么（Bruce：慈善代码 108 是宗教机构）。
  - 看各来源的产出和覆盖缺口（类型、地区），决定下一个找什么。
- **脚本做**：下载导出文件、按页抓名录、统计每个来源的规模和产出。
- **输出**：来源池里每一行记一个来源，带类型、规模、访问方式、状态和产出。
- **停止条件**：没有新来源可找，或者简报要求的覆盖面已经达到；产出低于 5% 的来源排到最后。

### 段2 建池团队：从来源到场地池和机构池

- **输入**：来源池里状态为"就绪"的来源。
- **agent 做**：
  - 写这份来源的读取方式：字段映射、筛选条件、哪些行不要。
  - 判断场地归哪个运营机构（例如一个市属场馆归市体育处，还是归外包承包商）。
  - 处理拿不准的合并：同名不同地、不同名同一机构。
- **脚本做**：批量入池（`pool`）；按名称加地点合并去重；把场地挂到机构下；标出范围不确定的行。
- **输出**：场地池（`venues.csv`）和机构池（`orgs.csv`）。新机构一入池，段3 就能开始处理。

### 段3 官网团队：为机构找到并确认官网

- **输入**：机构池里还没有确认官网的机构。
- **脚本做**：按名字加城市批量搜索；域名解析检查；识别共用门户（例如 paris.fr），定下本机构自己那一页作为范围。
- **agent 做**：判断搜到的网站是不是这家机构的（名字、地址、标题都对得上才算）；共用门户上找到本机构自己那一页；只在联合会页面或 Facebook 上有页面的机构，以那个页面为准。
- **输出**：每家机构的官网或主页，以及它的范围。
- 机构确认官网之后，脚本马上做**预扫**：读这家的高价值页面，抽邮箱，Jev 定级，结果存起来给段4 用。

### 段4 挖掘团队：从机构到联系人

- **输入**：已经预扫过的机构，每 15 家打成一批。
- **worker（agent 加脚本工具）一批的做法**：
  1. 看脚本返回的每家摘要：读了哪些页、找到什么、等级、哪里可疑。
  2. 对缺口逐家研究：没有确认 A/B 的、归属不清的、被挡的，agent 自己去搜、读 PDF、会议纪要、辖区页、联合会页、地图；所有页面都用 `fetch(org_id=...)` 读。
  3. 本批的待复核当场判断，写明理由。
  4. 每家写一行结论：找到了什么、在哪类页面、为什么判这个等级。
  5. 更新"找法手册"：这一类机构的联系人在哪、URL 规律、有效的搜索词、该找什么岗位。
- **页数**：按收益决定。只要还在读出新地址就继续读，名录翻页跟到底；连续两页没有新东西就停。
- **脚本放大**：找法手册更新后，脚本把同类机构的预扫按新找法重做一遍。后面领到批次的 worker，看到的已经是按新找法扫出来的结果。
- **输出**：联系人池（`contacts/`），每家机构都有结论。

### 段5 整理团队：复核、抽检、导出

- **agent 做**：
  - 处理挖掘团队留下的、跨机构的复核：同一地址出现在多家机构下，到底归谁。
  - 交付前从确认 A/B 里随机抽 100 条，逐条对照原页核对，计算准确率。
  - 把判不了的事整理进编号清单。
- **脚本做**：客户地址规则；合并去重（同一人两个地址只计一条）；选每家机构的首选联系人；对账；导出工作簿和路线 CSV。
- **项目结束时**：agent 跑 `learn`，把来源产出、有效页面类型、岗位词、纠正和找法手册写进 `references/projects/<市场>.md`。

## 3. 流水线、并行、并发

### 3.1 三层同时在动

| 层 | 内容 | 机制 |
|---|---|---|
| 段间流水 | 五段团队同时工作，上游一有产出下游就开工 | 池子加任务队列；每项都有状态（待处理、处理中、完成） |
| 段内并行 | 每段可以有多个 worker 同时领活 | 任务队列领取带租约，超时收回；一项同一时刻只归一个 worker |
| 调用并发 | 一个 worker 调一次脚本工具，脚本内部并发执行 | 多个读取器竞速、多个搜索引擎同时查、Jev 批量判；每家 provider 有自己的线程池 |

### 3.2 默认团队规模（可在简报里改）

| 段 | worker 数 | 说明 |
|---|---|---|
| 来源 | 2 | 一个按类型找，一个按地区补缺口 |
| 建池 | 1–2 | 来源多时加人 |
| 官网 | 1–2 | 机构多、门户多时加人 |
| 挖掘 | 4–8 | 主力 |
| 整理 | 1–2 | 越接近交付越多 |
| 协调 | 1 | 主会话 |

### 3.3 协调 agent 怎么调度

- 每隔几分钟看各池子的待处理数量：哪段积压就给哪段加 worker，哪段空闲就抽人去别段（例如来源找完了，来源组的人转去挖掘）。
- 合并各 worker 的找法更新，解决冲突，写回找法手册。
- 汇总编号清单交给用户；收到答复后写回简报或池子。
- 看总体指标：各来源产出、各段吞吐、`ab_routes_per_30_min`、准确率。

### 3.4 多 worker 同时工作的工程保障

- **写入互斥**：一项（一个来源、一家机构）同一时刻只归一个 worker。agent 正在处理的机构，脚本预扫不碰；脚本正在扫的机构，不派给 agent。
- **跨进程限速**：provider 的限速全项目共用（锁文件或本地服务），多个 worker 加起来也不超过各家的限制。
- **写文件安全**：联系人按机构分文件；临时文件名带进程号和线程号；共享文件加锁。
- **崩溃恢复**：所有状态写在磁盘上；worker 死了，租约到期后任务自动收回给别人；脚本进程由 supervisor 重启。

### 3.5 宿主适配

- 每段团队的作业说明写在 `references/roles/*.md`，与宿主无关；三家用同一份。
- 启动 worker 按宿主能力选：
  - 能起子代理或多智能体的，由协调 agent 直接起；
  - 能多开会话的，协调 agent 给出每个角色可直接粘贴的启动语；
  - 都不行的，协调 agent 自己轮流做各段。
- Claude Code、Codex、WorkBuddy 各自的启动写法，按各家当前文档实现，并在真机上验证。

## 4. 质量体系

| 层 | 措施 |
|---|---|
| 证据 | 每条都有来源页和引文；agent 也只能用 `fetch` 入库 |
| 归属 | 合并键用名称加地点；共用门户只有本机构那一页算本站；跨机构地址由 agent 判断归属 |
| 定级 | 简报写清等级定义和当地岗位词；客户规则优先；A 必须有人名；按实际负责场地、设备、外包的人排，不按职位高低 |
| 判断 | 每家机构都有 agent 看过并写结论；待复核由 agent 先判，判不了的才给用户 |
| 抽检 | 每次交付随机抽 100 条确认 A/B 核对，准确率 ≥ 90% |
| 金标准 | 每次发版跑 Bruce 法国 249 家已定级账户的真实对照：有 A+B 的机构占比 ≥ 37%，准确率 ≥ 90% |
| 回归 | 单元测试覆盖每条规则；模拟检查流程 |

## 5. 怎么衡量

- 广度：有确认 A+B 的机构占比；每百机构 A+B 路线数。
- 精度：抽检准确率；金标准对照。
- 吞吐：各段每分钟处理数；`ab_routes_per_30_min`；各段积压。
- 成本：provider 花费和 agent token 分开报；每家机构、每条 A+B 路线的成本。
- 投入：用户插话次数、编号清单条数。
- 贡献：每个来源、每一段、agent 补挖、找法手册各自新增了什么。

## 6. 与 Bruce 经验的对应

| Bruce 的痛点或要求 | 本设计的对应 |
|---|---|
| 时间耗在"等"和"重做"上 | 五段同时推进；状态写在磁盘上，断点续跑 |
| 流程不能停 | 一次简报、一张编号清单，其余自动推进；worker 死了任务自动收回 |
| 源头最重要 | 来源团队一直在找，按产出排优先 |
| 人工复核做不完 | agent 先复核，只有判不了的才给人 |
| 规则要沉淀 | 找法手册加 `learn` |
| 一套流程 | 一条业务链，按段分工，不拆成彼此等待的几个流程 |

## 7. 现状（0.6.6）和 0.7 要做的

| 部分 | 0.6.6 | 0.7 |
|---|---|---|
| 脚本层（读页、抽取、定级、并发、重启） | 有 | 改成 agent 调用的批量工具 |
| 任务队列 | 有（领取、租约、收回），默认不用 | 扩展为五段的队列，默认启用 |
| 来源池、场地池、机构池 | 有 | 加上状态，作为段间交接 |
| 来源团队、建池团队、官网团队 | 无 | 新增作业说明和工具 |
| 挖掘团队（agent 加脚本） | 只有可选的 `dig` 任务 | 默认；按批领取；预扫；找法手册；脚本放大 |
| 整理团队 | 只有可选的 `review` 任务 | 默认；跨机构归属；抽检 |
| 协调调度 | 无 | 看积压、调人、合并找法、汇总编号清单 |
| 写入互斥、跨进程限速 | 无 | 有 |
| 动态页数 | 固定 15 页 | 按收益决定 |
| 抽检、金标准对照 | 无 | 发版门槛 |
| Codex / WorkBuddy | 无 | 接入并真机验证 |
| agent token 计费 | 无 | 与 provider 费用分开报 |

实现顺序：
1. 写入互斥、跨进程限速。
2. 段间池子的状态和五段队列；协调调度。
3. 各段作业说明和工具：挖掘（批量扫、每家摘要、找法手册、脚本放大）先做，然后是来源、建池、官网、整理。
4. 动态页数。
5. 抽检表、金标准对照，作为发版门槛。
6. Codex、WorkBuddy 接入。

首次真跑：巴黎 929 家，对比 0.6.6 纯脚本的结果，看有确认 A/B 的机构占比、准确率、耗时、token。
