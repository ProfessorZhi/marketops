## 5. 精度与召回

### 5.1 原始输出：34 条 A/B 里 3 条不成立（91.2%）

| 类别 | 条数 | 为什么不成立 |
|---|---:|---|
| 地址属于同一张卡片上的**另一个岗位** | 1 | 卡片是"社区主管"，Jev 取了上一张卡（场地服务经理）的岗位词 |
| 缩写角色被当成设施岗 | 1 | `FS` 在英国小学是 **Foundation Stage**（学前班），与 Year 1–6 班长并列；被当成 facilities |
| 福利/保障类岗位 | 1 | 同一页上"设施官"与"俱乐部福利官"相邻，地址取到了福利官 |

三条都是**评级**错误，不是抓取错误：地址、姓名、岗位、原文都在页面上。

### 5.2 校正后：42/42 四项成立，2 条带保留

| 检查项 | 结果 |
|---|---|
| 字面存在（地址出现在保存的页面副本里，含 `mailto:`） | 42/42 |
| 同块绑定（姓名、岗位、地址在同一张卡片/同一段引言） | 40/42 |
| 岗位在口径内 | 42/42 |
| 未被排除 | 42/42 |

两条保留：一条的姓名在同一官网**另一页**的职员表里（联系页只写"询价：某某"）；
一条的地址是名字清单与地址清单**按位置对齐**（`sbm@` 型角色信箱，地址本身写着岗位）。

### 5.3 Jev 漏掉的 11 条：都在已抓到的页面上

| 类型 | 条数 | 例子（形状，不含真实值） |
|---|---:|---|
| 角色信箱（地址本身写着岗位）被判 C 或 X | 8 | `facilities@`、`ground@`、`caretaker@`、`bursar@`、`sbm@`、`Groundsman@` |
| 同一张卡片上前一张/后一张的岗位错位 | 3 | 场地助理 ×2、场地服务主管 ×1 |

即：**召回缺口几乎全在"地址即岗位"的信箱上**。这类地址不需要姓名绑定即可成立
（Bruce 的 `role_bound_public_email` 档），但 Jev 倾向于要求"人名 + 岗位 + 地址"三者齐备，
缺人名就降档。

### 5.4 还有 17 个账户：页面写了岗位，但没写地址

34 个无 A/B 的账户里，17 个的已抓页面上出现场地/设施岗位词，但**角色本人没有地址**
（有的整页只有一个通用信箱，有的用 `href="#"` 的 JS 按钮）。这一部分不是评级问题，
是站点本身没有可达地址。

## 7. 通用缺陷清单（任何行业都会出现）

1. **按引言绑定，在网格/卡片布局上整体错位一张卡。** Jev 给每条地址的引言，是**上一张卡片**
   的姓名与岗位。一张团队页上同时出现 1 条假阳性与 3 条假阴性——同一个 bug 的两种表现。
   复现：任何"头像+姓名+岗位+信封图标"重复卡片布局（Wix/Squarespace 模板常见）。
   `grades_snapshot`/`contacts.csv` 的 `quote` 与卡片内容差一位即可确认。
2. **角色缩写不做领域判断。** `FS Manager` 在英国小学是 Foundation Stage，与 facilities 同形。
   同类：`Site` 可指工地、`Ground` 可指咖啡渣。评级只看词形不看上下文时必然出错。
3. **"地址即岗位"的角色信箱被系统性低估。** `sbm@`、`facilities@`、`ground@`、`bursar@`、
   `caretaker@`、`Groundsman@` 这类地址，在缺少姓名时被判 C 甚至 X。本轮 11 条漏判里 8 条属于此类。
   这是与 1 相反的偏差方向：一个是过度依赖姓名绑定，一个是没有利用地址自带的岗位信息。
4. **JS/`href="#"` 的邮箱按钮永远拿不到。** 一个"员工目录"页面上有 25 张卡片、每张一个可见的
   "Email" 按钮，但页面里只有 2 个真 `mailto:`；其余地址在记录里根本不存在。
   这不是抓取深度问题，是**邮箱发现只看 `mailto:`/文本**的问题。
5. **同名指标三种分母。** `export` 的 `ab_orgs_per_100` = A+B **机构数** ÷ **账户数**；
   基线 = A+B **条数** ÷ **机构数**；TASK §8 = 同基线。三者相差一个数量级时谁也没报错。
   同一份输出里 `coverage` 也有两种定义（有 ABCD 行 vs 有任何行，97.7% vs 98.3%）未标注。
6. **通用入口与业务入口的标签不稳定。** `office@`、`admin@` 在有的机构判 C、有的判 D；
   `info@`、`contact@`、`enquiries@` 一律 D。同一规则在同一批次内不一致。
7. **`project()` 的作业列表会串项目。** 新建项目的 `crawl.jobs` 里出现了上一项目（44 目标）的
   作业记录；按项目隔离的进度视图与实际的全局作业表不一致。复现：建两个项目，各跑一次 `crawl`，
   在第二个项目上读 `project()`。
8. **交付面仍是 xlsx。** TASK §6 要 18 列 CSV，`export()` 给的是工作簿；18 列仍需操作员自己拼
   （rc15 的 bug 9 未修）。

## 10. 复现

```bash
# 1. 项目与简报（grades 用英国岗位名，照 Bruce 口径）
project("uk-pitchfinder-060-<date>", brief={goal, region, exclude, grades})

# 2. 输入：task_input.csv → 项目下的 orgs.csv
#    id = account_id, name = 机构名（去编号前缀）, website = official_url
# 3. 抓取（默认参数，不调 max_pages / workers）
crawl(project, "orgs.csv")
# 4. 评级
grade(project, limit=200)            # 重复到 still_ungraded = 0
# 5. 读 A/B 行，用 grade(set=[...]) 填 person/role 并纠正
# 6. 交付
export(project)
# 7. 量具（Tokyo-local）
python3 -I tools/convert_060.py      # → out/ukp_060_bruce18.csv / align.csv / metrics.json
```

量具与 rc16 同口径：`out/ukp_060_bruce18.csv` 是 TASK §6 的 18 列，
`out/align.csv` 逐账户四分类，`out/metrics.json` 是 §8 的全部指标（301 机构分母）。
