# 从 11 GB 会话语料里抽业务经验：这一轮工作流的教训

> 出处：本文由本机语料派生层装配（`ARTIFACTS_ROOT/marketops/bench/v0.6.2/bruce-knowledge/`），
> 该目录不随仓库分发。文中 `locator`（`voice/…`、`work-Wxx.md:行号`、`codex-<id>@<时间戳>`）
> 指向派生层文件，用于回查原话，仓库内无对应文件。语料本身（11 GB 会话、页面正文、第三方联系方式）不进 Git。

记录 2026-10-26 这一轮（S0 索引 → S1 抽取 → S2 66 个 worker/synth/verify agent → S6 落盘）里，
哪些步骤第一次就对了、哪些返工了、下一轮该怎么写。数字全部来自本地产物，不引用语料原文。

## 1. 量级：11 GB 里只有 0.15% 是人说的话和 agent 说的话

| 层 | 体积 | 说明 |
| --- | --- | --- |
| 语料总计 | 11 GB | `raw/` 2.3 G + `codex/` 7.5 G + `workbuddy/` 878 M |
| 抽取后人声 | 1.08 MB | 3,151 条 Bruce 本人消息（239 行索引 / 168 个唯一会话） |
| 抽取后 agent 侧 | 15.4 MB | 助手消息 + 工具调用名/参数摘要，**不含页面正文** |

结论：11 GB 的主体是工具输出（页面正文）与 `event_msg/item_completed` 对同一结果的重复记录。
抽取脚本（`extract_voice.py` / `extract_work.py`）把可分析面压到 16.5 MB，之后所有 agent 只读这 16.5 MB 的切片，
没有一个 agent 碰原始 jsonl。这是整轮能在 40 分钟内跑完、且不把第三方页面内容带进中间产物的关键。

下一轮沿用：先落一层「只含人声与调用名」的派生层，再并行。

## 2. 过滤注入块不是可选项：60% 的「用户消息」不是 Bruce 写的

8,007 条 `role=user` 里，4,825 条（60.3%）是注入块（system-reminder、task-notification、工具结果回填），
只有 3,151 条是他本人写的。不先滤掉，抽出来的「需求与不满」会大半是运行时噪声。

判据：`clean()` 先剥离 `<system-reminder>…</system-reminder>`，再看开头是否是已知的注入标签
（`<user_query>` / `<user_request>` / `<ask>` 除外）。逐条抽检 200 条，误杀 0 条、漏杀 0 条。

## 3. 失败的第一次归并：22% 覆盖率，原因在 schema 不在 agent

- worker 的发现 schema 允许 `project_line` 自由填写，实际写出了数百种值（`fr-grass-mowing`、
  `FR-天然草运动场`、`golf/FR`、`户外运动场-法国` …）。
- 归并 agent 按约定 `grep '"project_line":"<key>"'` 过滤，只捞到 886 / 4,022 = **22.0%**。
- 返工方法：不要再依赖文本标签，改从 `locator` 里的**会话 id** 做确定性归属。四层回退后覆盖率 100%：

| 依据 | 条数 | 占比 |
| --- | --- | --- |
| locator 内完整会话 uuid | 1,688 | 42.0% |
| 8 位短 id（`codex-xxxxxxxx` / `workbuddy-xxxxxxxx`） | 588 | 14.6% |
| 裸 8 位 id | 128 | 3.2% |
| 只给了分片名（`work-W27`）→ 该分片的 family 集合（单族才用） | 1,506 | 37.4% |
| `project_line` 关键词兜底 | 112 | 2.8% |

下一轮：worker 的输出 schema 里 `project_line` 必须是 8 个枚举值之一，且 `locator` 必须是
`<voice|work>/<source>-<uuid>@<iso8601>` 的规范形态——**归属靠 id，不靠标签**。

## 4. 会话 family 不能从 cwd 取

`extract_*.py` 第一版用 cwd 判业务线，结果：WorkBuddy 的 cwd 多是
`<HOME>\WorkBuddy\2026-09-20-14-59-54` 这类时间目录，104 个会话被判成 `other`；
另有 6 个会话的目录名在 jsonl 里是 UTF-8 被按 cp1251 解码的乱码，`高尔夫` 匹配不上。
还有一处语义陷阱：某项目目录叫「全球**非**高尔夫户外运动场」——只匹配 `高尔夫` 会把整整 6 个会话
（WorkBuddy 里最大的一批）错归到高尔夫线。

修正后的判定顺序：标题关键词（含 `非高尔夫` 否定预判、标题含「搭建/重构/报告/平台」等词时归跨线）
→ 标题缺失或乱码时，按该会话 voice 文本前 40 KB 的关键词计数取最大者 → 都没有才归跨线。
168 个唯一会话的最终分布：cross 63、fr-grass 25、golf 21、other 18、us 14、de 14、uk 11、ch 2。

## 5. 分母要按唯一键算，不要按行数

`index.jsonl` 有 239 行，但只有 168 个唯一会话——同一 codex 线程在不同归档文件里被拆成多行，
且多行带着不同标题（`迁移飞书机器人全部功能` / `美国运动场-发信和监控` 指向同一会话）。
凡是「多少会话」「覆盖率多少」都必须先去重到会话 id；本轮所有文档的分母统一写 168。

## 6. 核验 agent 只写报告，不会自己改；修复必须单独一道

4 个核验 agent 的产出是四份 `VERIFY-*.md`（抽样、隐私、数字、口径），共列出 13 处需要改的地方，
但没有任何一处被自动应用——agent 只在文档里写了建议。下一轮要么给核验 agent 写权限并明确
「发现即修」，要么单独排一个 fix 阶段。本轮采用后者：脱敏与对账由脚本机械执行，agent 不碰。

抽样核验结果（165 条）：实质性错误 5 条 = 3.03%（严格口径含引用不完整为 7.88%）。

## 7. 语料里的隐私面比预期窄，但绝对路径是常态

- 邮箱 / 电话 / 账号：在汇总层 0 命中（抽取时已把工具输出整层丢掉，页面正文里的 PII 进不了汇总）。
- 但 agent 写 locator 时会把 Windows 用户目录路径（盘符加 `Users` 下的用户名）原样抄进来，共 6 行，等于泄露 OS 用户名；
  另有 2 行把某个域名片段当证据写进正文。两类都要机械替换成 `<PATH>`，不交给 agent 判断。
- 结论：脱敏的重点不是「扫 PII」，而是「扫自己抄进来的路径」。

## 8. 时间口径：首尾跨度 ≠ 轮次时长

同一批法国调研同时存在两个读数：首尾跨度 740.9 小时（含夜间停机、等他回话的时间）与
333 轮的实际轮次时长 4.13 小时。文档里凡出现时长必须两个都报，否则「提速到 1/5」这类判据
会差 180 倍。这条已写进各线的「投入与成本」小节要求。

## 9. 可复用的流水线

```
S0 索引     1 个脚本，单遍扫语料，产出 voice/ + index.jsonl + work-manifest.jsonl
S1 分片     1 个脚本，按字节打包 + 超长单文件按行切分（最大片 369 KB）
S2 worker   24 voice + 40 work，各自读 1 个分片桶，只写 findings/*.jsonl
S3 归并     按「会话 id → 业务线」确定性过滤后，每线 1 个 agent，8 线
S4 专题     4 个 agent，各自从 8 份线文档 + 全量 findings 装配
S5 核验     4 个 agent，只读，出报告
S6 落盘     脚本：脱敏、对账、复制到 Git 工作树，只提交 8 份文档
```

规模：S2 一轮 66 个 agent、38 分钟、0 失败；返工的 S3/S4 用 12 个 agent、约 15 分钟。
两条经验——分片桶只装同一 business line（跨族桶会让归并 agent 读到自己不该读的内容），
以及每个 worker 的产出必须是「写文件」而不是「回消息」（回消息的正文会进主会话上下文，白烧上下文）。
