## 1. 法国族：他是怎么做的

### 1.1 工作被拆成 10 条 thread，按「步」而不是按「地区」

`derived/thread-inventory.csv`（法国族唯一 thread 10 条）：

| 角色 | thread 数 | turn 时长 | 说明 |
|---|---:|---:|---|
| 网页镜像 | 1 | 118.8 分钟 | 单条最长，占全族一半 |
| 邮箱质量 | 1 | 25.4 分钟 | |
| 飞书入库 | 1 | 23.4 分钟 | 交付通道 |
| 网页质量 | 2 | 24.0 分钟 | |
| 网页提取 | 2 | 32.2 分钟 | |
| 邮箱提取 | 1 | 10.9 分钟 | |
| 总协调 | 1 | 6.7 分钟 | 只调度，不做业务 |
| 机构完整性检查 | 1 | 6.5 分钟 | 独立一条对账线程 |

**教训**：他把「抓」与「判」分开成不同 thread，抓乱了不影响判，判改了只重跑判。
插件里对应的是 `browse` / `dig` / `review` 三类任务包分开。

### 1.2 法国市镇的「四页套路」

`derived/websearch-queries.csv`：1,000 条查询、1,901 次调用，其中 URL 型 405 条 / 911 次。
按路径首段归并：

| 路径 | 次数 | 用途 |
|---|---:|---|
| `/sports` | 153 | 体育服务页 |
| `/equipements-sportifs` | 146 | 体育设施清单页 |
| `/contact` | 131 | 联系页 |
| `/mentions-legales` | 104 | 法定声明页（法人的邮箱常在这里） |
| 其余 400+ 条 | 377 | 长尾，含 `/wp-content`、`/attachment` 等 |

四类合计 **534 / 911（59%）**。也就是说：法国市镇这一族，**先按这四条路径横扫，再谈别的**。
`/mentions-legales` 排第四很关键——它不是「关于我们」，是法国法律要求披露运营者身份的那一页，
常带一个可用的机构邮箱。

### 1.3 邮箱靠「反查」而不是「猜」

同一份 `websearch-queries.csv` 里，**184 次**是拿一个已有邮箱做精确检索（`"<邮箱>"`），
另有 `"<邮箱>" owner`、`site:<域名> "<姓名>" email`、`"<姓名>" "<机构>" email` 等形态。
这说明他的方法不是生成候选地址，而是：

1. 先在页面上拿到一个**真实出现过的**地址；
2. 再用搜索引擎把它和「人 + 机构」绑定；
3. 绑不上就不入表。

插件里 `likely_email` 那类猜测路径，按他的做法只能当**最后手段**，且必须标 `guessed`。

### 1.4 分级直接来自他的列前缀

`role_priority` 的取值前缀就是档位（`A_*` / `B_related_operator` /
`C_relevant_official_business_entry` / `D_official_general_research_entry`），
不需要另设映射。249 个可分级账户：A/B/C/D = 4 / 67 / 102 / 76（见
`docs/benchmarks/bruce-aggregate-062/SELECTION.md` §7.3）。

## 2. 跨项目方法（有证据支撑的）

来源：`docs/FINAL-REPORT.md` §3、§4（该报告已对这 11 GB 做过全量归并与对账）。

### 2.1 人的输入 > 全部自动路径

客户手给的一张名单一次带来 **31,262 条**可交接记录（报告 §4.3），
「远超所有自动抓取路径之和」。⇒ 建池前**先问客户有哪些现成清单**，这一句应写进 brief。

### 2.2 先算再爬

NL 那次先做「资产复用性审计」：985 个纯机构域里 **474 个已经抓到过角色箱**，
于是爬取量直接砍半（报告 §3.3）。⇒ 这正是 0.6.2 共享资料库该有的收益，
也是判定「复用省了多少」的现成口径。

### 2.3 三段式：上游物化 / 中间消费 / 下游验证

「唯一跑通吞吐的形态」（报告 §3.2）——重构后能一口气消费 33 个渠道，此前每批都停。
⇒ 对应插件的 `pool` / `run` / `export` 三段，不该在跑批中途改池。

### 2.4 引擎化：从「写脚本」变成「填源」

他把 33 列 schema + 去重 + 黑名单 + 对账固化成一个引擎后，新增一个国家从
「从零写脚本」变成「填源」（报告 §3.3）。⇒ 每加一个国家的成本应该是**一份源清单**，
不是一次开发。这条是 `marketops-sources` 该有的姿态。

### 2.5 门禁：不可变队列 + 授权清单 + 哈希绑定 + fail-closed

同一形态在 2,163 封上做到 0 失败 0 重复（报告 §3.3）。⇒ 这条已经进了插件，保留。

## 3. 反模式（可直接写成 skill 的「不要做」）

| 反模式 | 证据 | 插件里的对照 |
|---|---|---|
| **心跳 ≠ 爬虫** | 14 分钟只增 8 页；同段 prompt 重放 131 拍只换来 131 句状态复述 | 定时轮询不是推进 |
| **调大并发反而更慢** | 4 worker 反而把 50 页从 13 分钟拖到 24 分钟 | 并发要压测，不能拍脑袋 |
| **脚本爆炸** | ~30 个 `qualify_*.py`、≥18 个 `build_batch0NN_*.ps1` | 同类任务参数化 |
| **失败后没有第二轮策略** | 自动化挂着不收敛，1.9 天零回复 | 每类失败要有重试或放弃判据 |
| **用行数判完整** | `len(rows) >= total` 会被重复行掩盖 | 完整性按唯一键 |
| **漏斗极陡却按「页」报进度** | 220 页严格判定只出 5 条 / 4 个 URL；224 个唯一邮箱只出 22 条合格路线 | 进度要按**合格路线**报，不按页 |

最后一条对出题最关键：**万级输入、几十条输出**是常态。用「页面数」当产出会系统性高估。

## 4. 一处必须修的判定基线：Bruce 的「时长」

`PROJECTS.md` 与 `SELECTION.md` 记的 740.9 小时是**首尾跨度**（含跨夜空闲）。
同一批 thread 的 **turn 时长合计只有 248 分钟（4.13 小时）**，333 个 turn，10 条 thread
（`derived/thread-inventory.csv`，按唯一 `thread_id` 取，勿直接 `wc -l`——那张表是
快照追加表，324 行只对应 187 个 thread，重复计会虚高 1.73 倍）。

| 口径 | 值 | 含义 |
|---|---:|---|
| 首尾跨度 | 740.9 h | 上界，含全部空闲 |
| turn 时长合计 | 4.13 h | 下界，只算代理执行 |
| turn 数 | 333 | |
| 人工往返 | 422 条用户消息 | 最接近「人工投入」的量 |

⇒ 判定「插件总时长 ≤ Bruce 的 1/5」现在同时可以读成 **≤148 小时** 和 **≤49 分钟**，
两者差 180 倍。冻结基准前必须选定一个口径；建议用 **turn 数 + 往返数**当投入代理量，
时长只作参考。
