# 下一轮等条件复测建议（尚未执行）

本方案是后续实验设计，本次未启动新会话、未搜索场馆、未调用收费接口，也未修改配额或凭据。

## 先固定问题

1. 明确巴黎市区还是 Île-de-France，固定场馆类型、室内判定标准与去重单位。场馆、运营组织、地图点位分别编号。
2. 确定产品或服务、目标采购岗位。若仍未知，只评估联系人候选质量，不给“高 ROI”结论。
3. 从独立权威目录构建同一份 10—20 家场馆底表，包含不同场馆类型。用同一输入分别运行 A/B，禁止一组只找大场馆、另一组做泛地图扩池。
4. 两组使用相同模型、相同工作时长、相同硬性调用/金额上限、相同付费代理设置。记录实际型号和停止原因；缺少 token 账单时保持未知。
5. 每组至少重复三次，轮换顺序。分别控制是否允许共享历史材料和经验，避免缓存或前一场已找到答案造成偏差。

## 统一验收

| 指标 | 合格条件 |
|---|---|
| 场馆身份 | 有场馆身份、地址、室内类型和一手来源；地图 POI 不能直接计为已验证场馆 |
| 组织关联 | 证明运营/拥有关系，处理品牌与法律主体差异 |
| 具名联系人 | 姓名、当前岗位、组织关系和公开字面邮箱完整关联 |
| 邮箱上下文 | 区分采购、运营、销售、招聘及共享入口；招聘邮箱单独标注 |
| 用户排除项 | 通用、前台、工单、订票入口不能进入个人决策人合格数 |
| ROI | 只有产品、买方和判断标准明确时才排序，否则为未知 |
| 数据对账 | 输入池每个 ID 都有研究结论；候选、HOLD、准入和导出逐层对账 |
| 费用 | 区分工具次数、底层尝试、token、费率估算、未知账单和已结算金额 |
| 交付 | 两组使用相同字段、文件格式与证据列；导出成功与研究成功分别判断 |

## 复测前需解决的已观察问题

- 国家参数：确认 `France` 的处置方式和两位国家码提示。用修正的 `FR` 做一次明确计入预算的连通性测试后，再判断真实搜索可用性；本次只完成纯函数复现。
- 本地抓取：在真实受管浏览器中完成一次有边界的抓取，READY 才代表该能力通过验收；持续不可用时本轮应跳过该路径。
- 具名岗位：不能在人员和岗位未准入时，把邮箱路线宣称为完整个人决策人交付。修复组织证据关系与导出一致性。
- 错误返回：将参数校验、能力不可用、传输失败和供应商错误分开，不根据 `IDENTITY_VALUE_INVALID` 建议更换 Key。
- 证明链：明确修复 `BLOCKED_LEDGER_NOT_WIRED` 的证据信封导出关联，同时保留已有账本。

最终结果只统计符合统一定义的数量和实际可观察费用。若目标总体没有可信分母，就报告底表完成率，不报告全巴黎覆盖率。
