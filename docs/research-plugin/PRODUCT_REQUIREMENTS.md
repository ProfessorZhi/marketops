# MarketOps 调研插件 · 产品需求与交付标准

版本：2026-10-20　状态：**需求基线**（后续开发与验收都以本文件为准）
依据：用户需求原话（2026-10-20 会话）、`ProfessorZhi/marketops-session` 对 Bruce 工作记录的分析
（`docs/FINAL-REPORT.md`、`docs/BRUCE_TAKEOVER_SCORECARD.md`、`docs/BRUCE_INTERVENTION_MAP.md`）、
当前插件代码（`plugins/research-tools/marketops-research-assistant/`，0.5.7-rc6）。

---

## 0. 一句话定义

**一个可以装进 Codex / WorkBuddy / Claude Code 等 agent 的插件。它内置 Bruce 的业务知识，
带一个多个对话共享的数据库。它把「需求 → 母池 → 场地池 → 组织池 → 联系人/路线池 → 报告与交付」
整条工作流跑通。五家工具都在正常流程里被真正用到。它能长时间自主运行、多对话并发、
处理大规模任务，在任何市场都能做研究，而不是只为某个测试场景调优。**

不是：
- 不是针对英国草坪 / 埃塞克斯板球场的专用脚本；
- 不是「接入了某个供应商但从来不调用」的接口展示；
- 不是每做几页就停下来问人的半自动玩具；
- 不是只能在一个对话、几十条目标规模下工作的演示。

## 1. 功能需求

### R1 业务知识真正融合（不只是文档）

Bruce 的业务判据必须成为**会被执行、会拦东西、拦不住会报错**的规则，
而不是写在 Markdown 里让 agent 自己记住。来源：干预图谱中 `POLICY` 22 条 + `GUARD` 23 条。

| 编号 | 业务规则（Bruce 原判据） | 必须落在哪 |
|---|---|---|
| R1.1 | 目标函数是「**邮箱可见性优先**」，不是「场地规模优先」（INT-010） | 发现与排序阶段的打分 |
| R1.2 | 「一主体多场地」：按组织扫描，姓名不是必要条件（INT-033） | 实体模型与 Brief |
| R1.3 | **角色优先级表**（由真实回复反推）；买设备干活的是客户，卖设备的是竞品（INT-052） | 场景包里的机器可读角色表 → Jev 角色打标 → 路线评级 |
| R1.4 | 打总机不算有效，必须明确指到人或部门（INT-062） | 路线评级（A/B/C/D）硬规则 |
| R1.5 | 样本批 ≠ 全池；投递成功 ≠ 完成；数下游落盘才算（INT-009 / INT-011） | 完成判定与报告 |
| R1.6 | **抑制 / No-Go / 退订名单**在任何对外动作之前一票否决；找不到名单就 BLOCK，不当作「干净」 | 交付门禁（当前插件代码里**没有**，见 §4） |
| R1.7 | 口径有版本号；改口径时报出受影响的记录范围，而不是整批回炉 | 规则版本 + 记录上的 rule_version |

**通用与场景分层**：主流程只认通用概念（目标类型、想要的角色、地域、合格条件）；
某个市场的知识（角色表、合格条件、名录来源、命名习惯）全部放在**场景包**里。
新市场 = 新场景包，主流程代码不改。没有场景包时也能跑，只是由 agent 从需求里生成一份临时场景包并在报告中标明。

### R2 工作流端到端打通（从需求到报告）

```text
需求（可来自多轮对话）
  → Brief（结构化：目标类型、角色、地域、数量、预算、规则版本）
  → 母池（候选来源 + 去重 + listed = imported + duplicate + rejected 对账）
  → 场地池 / 组织池（实体、owner/operator 关系、资格判定）
  → 联系人 / 路线池（人或部门、角色、字面邮箱、证据引用、A/B/C/D 评级）
  → 校验（verifier 抽检证据原文）
  → 报告 + 交付表（XLSX/CSV + manifest + 未完成项清单）
  → 复盘经验（回写场景包的「建议」，人批准后才生效）
```

验收要求：
- 每一级池子都是**数据库表**，不是 CSV 或聊天记录；下一级只从上一级读，不从对话上下文读。
- 每一级都有「进入多少 / 产出多少 / 去重多少 / 拒绝多少 / 未处理多少」的对账，**不能用减法反推**。
- 任何一级可单独重跑，结果幂等。
- 需求可以分多次对话补充：后来的对话读到同一个 Brief 和同一批池子，不重新开始。

### R3 共享数据库

- 一个数据根目录、一个权威数据库；所有对话、所有宿主（Codex / WorkBuddy / Claude Code）读写同一份。
- 池子是**跨 Run 持久**的：第二个任务先查已有池子，只补缺口（「合格组织缺负责人」「有人缺现职证据」）。
- 并发安全：领取用租约（lease），对话崩溃后租约到期自动回收。
- 规模目标：单个池子 **≥ 50,000 个目标**、**≥ 8 个对话同时写**而不丢数据、不死锁。
  SQLite（WAL）是单机默认实现；数据层要隔一层接口，以后可换成 Postgres，支持多机。
- 报告和看板的数字**只从数据库算出来**，不读快照或状态字段（Bruce 记录里看板数字「在十个数之间横跳」）。

### R4 五家工具都在正常流程中被使用

| 工作 | 工具 | 什么时候必须用 |
|---|---|---|
| 找目标 | **Serper** + **SerpApi**（含地图）+ **TinyFish Search** | 发现阶段默认三家并查、合并去重；任何一家没用要在报告里写原因 |
| 读网站 | **Crawl4AI**（本地，免费） | 默认读取器 |
| Crawl4AI 读不了的 | **TinyFish Fetch** | PDF、纯 JS 空页、Crawl4AI 判定疑似被拦的页面 |
| 大批量判断 | **Jev（TypeSafe）** | 每个组织的范围分诊（在不在范围内）+ 每个邮箱的角色打标；**有角色表就必须调用** |
| 难站点 | **TinyFish Agent**（付费） | 仅在用户授权的预算内 |

验收：每次正式运行结束，报告里列出五家各自的调用次数、花费、成功率；
**某家调用为 0 且没有书面原因 = 验收失败**。真正的封锁 / 验证码页面一律停止，任何工具都不绕过。

### R4.1 Jev 和 Crawl4AI 的「真正使用」

- **Jev**：不是「接了 SDK」。它的判断结果必须写进池子（scope 字段、角色标签），
  并且被下游使用（路线评级读角色标签；范围外的组织不再进入联系人研究）。
  只调用不消费 = 没用。
- **Crawl4AI**：不是「能启动」。正常流程中 ≥ 80% 的网页读取由它完成；
  它读出的材料带 SHA-256 落盘，证据引用指向这份材料。

### R5 自动化与长任务

来源：职责 17「调度」与职责 20「成本控制」是记分卡上唯二 `NOT_BUILT` 的项，
Bruce 在 5 个以上线程、两个月里反复要求「不要让我点继续」。

- 用户在开头确认一次：范围、预算上限、角色定义、是否允许付费工具。之后**不再停下来问**。
- 只有四类事情可以停下来问人（干预图谱里结构上必须人做的四类）：**授权、取舍、定义、裁决**。
  其他情况（某个站点失败、某家工具报错、某批结果少）自己处理并记录。
- 预算熔断：花到上限自动停，报告里写「因预算停止」，**和「跑完了」在状态上必须不同**。
- 看门狗：一批跑完既没交付也没开始下一批 → 自动继续或报警。
- 断点续跑：宿主退出后再次打开，从数据库里的进度继续，不重复花钱。
- 一个大任务能拆成多个子任务分给子 agent / 多个对话并行，结果汇到同一个池子。

### R6 规模与并发

- 支持 **多个对话并发调研同一任务**（共享池子 + 租约），以及 **多个任务同时跑**（各自 Run，共享实体去重）。
- 单任务目标：**1,000 个组织级别**在无人值守下跑完；池子容量 ≥ 50,000。
- 每家工具有并发上限与限流退避；全局预算跨对话统一计数（已有 provider-reservations 台账）。

### R7 证据与可信度（「空转的绿」防线）

来源：Bruce 记录的第一号失效模式。

- 验收读**正文实体**（字节数 + source_ref + SHA-256 + 原文引用），不读状态字段。
- 空值 ≠ 0 ≠ 通过；找不到输入就 BLOCK。
- 「抓到的条数 vs 落库的条数」强制对账；静默丢弃即失败。
- verifier 对交付记录做随机抽检，抽检通过率进报告。

### R8 安装与交付

- 一条命令安装到 Codex / WorkBuddy / Claude Code，四个 key 一次配置，存在系统凭据区，不进仓库、不进日志。
- 安装后 `/marketops-setup` 自检：五家各发一个最小请求，报告可用 / 不可用。
- 交付物：报告（Markdown/HTML）、交付表（XLSX + CSV）、manifest、未完成项清单、复盘经验。

## 2. 通用性验收（防止只针对测试优化）

一个版本只有同时通过下面三项才算「可交付」：

1. **三个互不相关的市场，代码不改**：
   - 英国草坪 / 运动场地（有场景包）；
   - 美国 Austin 联合办公（无场景包）；
   - 第三个从未跑过的市场（例如德国物流园、日本私立学校），由用户临时指定。
2. 三次运行都：**无中途提问**跑完；五家都有调用记录或书面原因；verifier 抽检 ≥ 80%；
   池子对账无 `UNACCOUNTED`；报告数字与数据库一致。
3. 至少一次运行用 **≥ 3 个对话并发**，目标 ≥ 300 个组织。

A/B 联系人数量不设统一及格线（受市场是否公开邮箱影响），但报告必须给出
「为什么只有这么多」的证据化解释与下一步数据源建议。

## 3. 现状对照（0.5.7-rc6，`ac2eefc`）

| 需求 | 现状 | 结论 |
|---|---|---|
| R1 业务知识 | 场景包机制已有（`ACCEPTANCE_PROFILE_UK_GRASS.md`）；通用命名规则已改；BUSINESS_PLAYBOOK 是文字说明 | **部分**：角色表未做成机器可读并强制驱动 Jev；R1.6 抑制名单在插件代码中**不存在** |
| R2 端到端 | Brief → 发现 → 抓取 → 候选写库 → verifier → 交付表已能跑通（Essex×2、Austin×1） | **基本通**；池子分级（母池/场地/组织/联系人）目前是一张目标池 + 每 Run 的候选表，不是跨 Run 的分级池 |
| R3 共享数据库 | `research_pool.py`：SQLite WAL + 租约 + busy_timeout，多对话可共享；单次导入上限 5,000 | **单机可用**；≥8 对话 / ≥50,000 规模**未压测**；无 Postgres 抽象 |
| R4 五家工具 | Austin 运行：Crawl4AI 115、TinyFish fetch 11、Serper 35、SerpApi 13；Jev 0、TinyFish search 0。`ac2eefc` 已改默认路径 | **修复已提交，未经实跑确认** |
| R5 自动化 | Essex 第 2 次与 Austin 均无中途提问；预算台账已有 | **部分**：无看门狗；预算停止与完成的区分需核验；跨对话自动续跑未做 |
| R6 规模 | 最大实跑约 86 个组织、16 个子 agent | **未达标**（目标 1,000） |
| R7 证据 | verifier 抽检 Essex 5/14 → Austin 8/9 | **明显改善** |
| R8 安装 | 安装器 + setup 已有；要求 Python 3.12 | **可用**；三宿主实机安装未在本环境复验 |

**测试**：插件测试套件在 Python 3.12 下除 8 个失败外全部通过，这 8 个需要真实代理 / 网络或宿主安装环境，
与 rc6 改动无关。

**结论：目前还不能交付。** 最大的三个缺口：
1. Jev / TinyFish Search 的修复没有经过一次实跑确认（R4）；
2. 抑制 / No-Go 名单完全缺失（R1.6）。这是 Bruce 记录里代价最大的事故（二次投诉）；
3. 规模与并发没有压测（R3/R6），分级池子没有跨 Run 持久化（R2）。

## 4. 交付路线（按顺序）

| 步骤 | 内容 | 完成标志 |
|---|---|---|
| S1 | 用真实 key 跑一次 Austin 复验 | 五家都有调用记录；Jev 结果被路线评级读取 |
| S2 | 角色表机器可读 + Jev 强制消费；抑制 / No-Go 名单入库并作为交付门禁 | 单元测试 + 一次实跑里能看到被拦下的记录 |
| S3 | 分级池子：母池 → 场地/组织池 → 联系人池跨 Run 持久化；第二个任务先复用再补缺 | 第二次同市场运行的新增花费明显低于第一次 |
| S4 | 看门狗 + 预算熔断状态区分 + 断点续跑 | 人为杀掉对话后重开能续上，不重复计费 |
| S5 | 并发与规模压测：8 对话 × 50,000 目标池（模拟）+ 1 次 ≥300 组织实跑 | 无丢失、无死锁、对账全平 |
| S6 | 第三市场盲测（§2） | 三市场全部通过 §2 的标准 |

S1–S2 完成可发**内部试用版**；S1–S6 全部完成才算**可交付版**。
