## 三、质量:三个不同的数字,别互相替代

这一轮同时存在三个「准确率」，它们的分母和时点都不同：

| 数字 | 定义 | 时点 |
|---|---|---|
| **43.2%(19/44)** | finish 线程自己的 44 行抽检 | ~14:2x，较早 |
| **61.7%(192/311)** | 工作簿口径：全部已核对行中判为 ok 的比例 | 14:59 |
| **175/182 已核 ok** | 现存的 A/B 行里有 175 条被标 ok、7 条未核、**0 条被标 wrong** | 14:59 |

**为什么第三个不能当精确率读**：错的 119 条已经在复核里被改级移出 A/B 集了，剩下的自然是「核过的都对」。这是**事后过滤过的样本**，不是无偏估计。能拿来对照 90% 门槛的是中间那个 **61.7%**——它跨全部 311 条已核对行，仍然不达标。

**43.2% 与 61.7% 不矛盾**：前者是同一天更早、更小、且集中在问题最严重的机构上的样本；后者样本更大、覆盖更广。**引用时应说明分母**，不能挑一个说事。

误判不是散点，是五种固定模式：

1. **名录页绑定**（最大一类，约 230 条）—— 市府协会 annuaire、区级活动指南、联合会俱乐部名单上的人员，被挂到了宿主场馆上。名录页面上的联系人属于**被列出来的那个俱乐部**，不属于场馆。
2. 外市页面（Nevers、Montivilliers）的内容绑到巴黎机构；
3. 连锁加盟总部的「franchise 开发」岗当成门店路线；
4. 外协会人员混进来（如另一联合会的负责人挂到本联合会下属中心）；
5. 同一俱乐部的主场地与附馆混淆。

之后按同一模式批量改级约 266 条为 X。

**另一件容易误读的事**：`stages.check` 那个计数（`mo_workspace.py:617-627`）只统计 `checked in ("ok","wrong")` 的**已复核行**，不区分这些行现在还在不在 A/B 集里。它既不是抽检精确率，也不是当前 A/B 的质量。

## 四、供应商失败分布:本轮不是被限流拖垮的

先证伪了一个假设。中途吞吐掉到 **2 家/分钟**，看起来像限流；但宿主 128 核、负载仅 21，`429` 全程只有 **6 次 / 6,345 次调用 = 0.09%**，且全部落在 `crawl4ai`。把 `workers` 从 6 提到 10 后回到 **4.5 家/分钟**。结论：**不降并发**。

| 读者 | 失败率 | 主要构成 |
|---|---|---|
| tinyfish | 45% | bot_blocked 309 / target_unreachable 187 / target_http_error 135 / page_not_found 95 / proxy_error 44 / invalid_url 42 / no text 34 |
| deepseek | 52% | HTTP 404 894 / 504 64 —— 目标页真的不存在或超时,不是被挡 |
| crawl4ai | 51% | Cloudflare 296 / 内部异常 114 / 403 94 / minimal_text 43 / Akamai 11 / **429 仅 6** |

失败主体是**网站本身不可读**（404、Cloudflare、目标不可达），不是配额。这决定了后续优化方向：换读者组合与换页面类型，而不是加钱或降速。

## 五、经验

### 研究层

1. **判级只判「这个人合不合规」，不判「这个人属于不属于这家机构」**。误判几乎全在归属边上。单行看，`quote` 有姓名有职务、邮箱格式也对，判 A 完全成立——错的是那条边没人看。准入检查要问「这个人属于哪家机构」。
2. **名录页（协会 annuaire、活动指南、联合会名单）不能作为场馆的联系人来源**。俱乐部联系人只有在「场馆本身就是该俱乐部」时才算路线。已验证的例外：本区 `en charge du sport` 的民选副区长为 A，市府 territoire 主任对其辖区每家场馆为 B。
3. **同一 URL 两个读者结果不一致时没有裁决规则**，这是流水线缺陷，不是读者缺陷。tinyfish 把 ROT13 混淆邮箱原样返回（`@cnevf.se` 即 `@paris.fr`），crawl4ai 读同一页给出真址，两者都进表 → 伪地址被当 A/B。处理口径：伪址判 X，**不手工解码回写**（那等于用变换代替取证），要真址就用 `readers=["crawl4ai"]` 重读让真址带引文入新行。
4. **没有搜索引擎时的广度天花板**：本轮全靠 deepseek + tinyfish，广度 14.1%，每百机构 A+B 路线 19.7。0.6.6 那轮 A+B 密度是 9.1 行/家，但其中大量来自名录页泛滥——折算下来质量差距没有行数差距那么大。
5. **一条联系人同时挂在多家机构上是可用的信号**，不是噪声：一位区级主管体育的副区长同时出现在 8 家机构上，说明该区体育事务集中在一人手里。但它应该是 **1 条 B + 7 条说明**，不是 8 条 A。

### 工程层

1. **`run(stop=True)` 留下的 `STOP` 可能删不掉**。`mo_run.py:594-595` 只在「看不到别的活进程」时删；多分片同时退出时是竞态，谁都看得见别人活着，于是谁都不删。重启后每个分片读到 `STOP` 立刻 `done=True`、`stopped_because: "stopped on request"`、flow 全 0——**看起来像跑完了**。重启前一律先 `ls STOP`。
2. **有活进程时重启不会清 `STOP`**：`run()` 只在 `if pids: return already_running` 之后才 unlink（`mo_run.py:667-672`）。「以为重启了其实没动」有两种成因，要分开查。
3. **密钥轮换的生效边界是进程环境**。CC 进程的 env 启动时定死，MCP 子进程继承旧值；改 vault 文件对已启动的 MCP 无效。想立刻用新 key，得从 source 过新文件的 shell 起 `server.py`。
4. **402 这类供应商拒单没有降级路径**。`mo_grade.one_batch` 遇 402 直接 `mark_exhausted("jev", …)` 并把整批记失败，没有 fallback。1,731 条联系人因此卡住，KPI 停涨但扫描照跑，从外面看只觉得「跑得慢」。
5. **「完成」必须从产物读，不能从状态行读**。这一轮 `done=True` 出现过两次假阳性（一次 STOP、一次分片空转）。判据是 `contacts.csv` / `crawl.csv` 的行数与对账，不是 `run.*.json` 的 stage。
6. **中途汇报不可信，收尾对账才可信**。本轮同一批数据在 30 分钟内给出过三组互相矛盾的 A/B 数与准确率（见 §三）。任何对外数字都应回到导出时的对账页取，而不是采信工作线程的口头总结。

## 七、停机状态与恢复方式

停机时：`server.py supervise|run` 进程 **0**，8 个 worker 全部停止，`STOP` / `POOL_DONE` 均不存在。产物完整、无半截行（`contacts.csv` 18,927 / `orgs.csv` 918 / `verdicts.csv` 988 / `tasks.csv` 134 / `crawl.csv` 1,560 / `playbook.json` 可解析）。

恢复跑：

```sh
# 必须从 source 过新 vault 的 shell 起，MCP 内跑仍用旧 key
cd /data/home/vince/MarketOps/v0.7.0/paris-indoor-070
ls STOP                      # 有就先确认内容再删
venv/bin/python scripts/server.py supervise paris-indoor-070 \
    --shards 4 --opts '{"workers":10,"rounds":4,"max_pages":20,"follow":true}'
```

剩 **约 509 家未抓取**。恢复后第一件该做的不是扩量，是把抽检补到能支撑 90% 判定的规模，并把那 7 条未核的 A/B 逐条开页。
